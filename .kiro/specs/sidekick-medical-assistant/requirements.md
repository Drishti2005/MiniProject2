# Requirements Document: Sidekick AI Medical Appointment Assistant

## Introduction

Sidekick is a real-time AI-powered web application designed to assist patients during medical appointments by listening to doctor-patient conversations, simplifying complex medical terminology into plain language, suggesting relevant clarification questions, generating structured visit summaries, and providing optional translation services. The system aims to improve patient understanding and engagement during medical consultations by providing real-time assistance without disrupting the natural flow of conversation.

## Glossary

- **System**: The Sidekick AI Medical Appointment Assistant application (frontend + backend)
- **Session**: A single doctor-patient conversation instance from start to end
- **Transcript_Chunk**: A segment of recognized speech text sent from the browser to the backend
- **Medical_Term**: Clinical or medical terminology that may be unfamiliar to patients
- **Simplification**: A plain-language explanation of a medical term
- **Question_Suggestion**: A clarification question generated by the AI that the patient could ask
- **Visit_Summary**: A structured summary of the entire medical appointment
- **Web_Speech_API**: Browser-based speech recognition API (SpeechRecognition)
- **Gemini_API**: Google's Gemini AI language model API
- **WebSocket**: Bidirectional real-time communication protocol
- **Supabase**: PostgreSQL database service for data persistence
- **Frontend**: Browser-based user interface (HTML/CSS/JavaScript)
- **Backend**: FastAPI Python server handling WebSocket and REST endpoints
- **Translation**: Converting text from English to the patient's preferred language

## Requirements

### Requirement 1: Real-Time Speech Recognition

**User Story:** As a patient, I want the system to automatically transcribe the doctor-patient conversation in real-time, so that I can see what is being discussed without manual note-taking.

#### Acceptance Criteria

1. WHEN the user clicks the "Start Recording" button, THE System SHALL request microphone permission from the browser
2. WHEN microphone permission is granted, THE System SHALL activate the Web_Speech_API in continuous recognition mode
3. WHEN speech is detected, THE System SHALL display interim results in the transcript panel
4. WHEN a speech segment is finalized, THE System SHALL send the Transcript_Chunk to the Backend via WebSocket
5. WHEN the user clicks the "Stop Recording" button, THE System SHALL terminate speech recognition and close the session
6. IF the Web_Speech_API is not supported by the browser, THEN THE System SHALL display an error message indicating browser incompatibility
7. WHEN speech recognition encounters an error, THE System SHALL log the error and attempt to restart recognition automatically

### Requirement 2: Medical Terminology Simplification

**User Story:** As a patient, I want complex medical terms to be automatically explained in simple language, so that I can understand what the doctor is saying without interrupting to ask.

#### Acceptance Criteria

1. WHEN a Transcript_Chunk is received by the Backend, THE System SHALL send it to the Gemini_API for medical term analysis
2. WHEN the Gemini_API identifies Medical_Terms in the transcript, THE System SHALL generate plain-language Simplifications for each term
3. WHEN Simplifications are generated, THE System SHALL send them to the Frontend via WebSocket within 2 seconds
4. WHEN Simplifications are received by the Frontend, THE System SHALL display them in the "Simplified Terms" panel with the original term and explanation
5. WHEN no Medical_Terms are detected in a Transcript_Chunk, THE System SHALL not send empty simplification messages
6. THE System SHALL maintain a list of all Simplifications for the current Session
7. THE System SHALL store each Simplification in the Supabase database with session_id, term, explanation, and timestamp

### Requirement 3: Question Suggestion Engine

**User Story:** As a patient, I want the system to suggest relevant questions I could ask the doctor, so that I can better understand my condition and treatment without forgetting important topics.

#### Acceptance Criteria

1. WHEN the Backend receives Transcript_Chunks, THE System SHALL accumulate them to build conversation context
2. WHEN sufficient context is available (minimum 3 Transcript_Chunks), THE System SHALL send the conversation context to the Gemini_API for question generation
3. WHEN the Gemini_API generates Question_Suggestions, THE System SHALL return 2-3 relevant clarification questions
4. WHEN Question_Suggestions are generated, THE System SHALL send them to the Frontend via WebSocket
5. WHEN Question_Suggestions are received by the Frontend, THE System SHALL display them in the "Suggested Questions" panel
6. THE System SHALL update Question_Suggestions as the conversation progresses with new context
7. WHEN the conversation topic changes significantly, THE System SHALL generate new Question_Suggestions relevant to the current topic

### Requirement 4: Real-Time WebSocket Communication

**User Story:** As a user, I want the system to provide instant feedback and updates during the conversation, so that I can follow along without delays.

#### Acceptance Criteria

1. WHEN the Frontend loads, THE System SHALL establish a WebSocket connection to the Backend at ws://localhost:8000/ws/session
2. WHEN the WebSocket connection is established, THE System SHALL create a new Session in the Supabase database
3. WHEN the Frontend sends a message via WebSocket, THE Backend SHALL receive and process it within 100ms
4. WHEN the Backend sends a message via WebSocket, THE Frontend SHALL receive and display it within 100ms
5. IF the WebSocket connection is lost, THEN THE System SHALL attempt to reconnect automatically up to 3 times
6. WHEN the WebSocket connection fails after 3 attempts, THE System SHALL display an error message to the user
7. THE System SHALL support the following WebSocket message types: transcript, simplification, questions, translation, summary, end_session

### Requirement 5: Visit Summary Generation

**User Story:** As a patient, I want a structured summary of my medical visit at the end of the appointment, so that I can review key information and share it with family or caregivers.

#### Acceptance Criteria

1. WHEN the user clicks "Stop Recording", THE System SHALL send an end_session message via WebSocket
2. WHEN the Backend receives an end_session message, THE System SHALL compile all Transcript_Chunks for the Session
3. WHEN the full transcript is compiled, THE System SHALL send it to the Gemini_API with a summary generation prompt
4. WHEN the Gemini_API generates a Visit_Summary, THE System SHALL extract structured fields: title, diagnosis, medications, instructions, follow_up, and key_points
5. WHEN the Visit_Summary is generated, THE System SHALL store it in the Supabase summaries table
6. WHEN the Visit_Summary is stored, THE System SHALL send it to the Frontend via WebSocket
7. WHEN the Frontend receives the Visit_Summary, THE System SHALL display it in a dedicated summary view with all structured fields
8. THE Visit_Summary SHALL be generated within 10 seconds of session end

### Requirement 6: Multi-Language Translation

**User Story:** As a non-English speaking patient, I want the system to translate medical explanations into my preferred language, so that I can understand the information in my native language.

#### Acceptance Criteria

1. WHEN the Frontend loads, THE System SHALL display a language selection dropdown with supported languages
2. WHEN the user selects a language other than English, THE System SHALL store the language preference for the Session
3. WHEN Simplifications are generated and a non-English language is selected, THE System SHALL send the Simplification text to the Gemini_API for translation
4. WHEN the Gemini_API returns translated text, THE System SHALL send it to the Frontend via WebSocket
5. WHEN translated text is received, THE System SHALL display it in a dedicated translation panel below the main interface
6. THE System SHALL support translation for at least the following languages: Spanish, Hindi, Mandarin, French, Arabic
7. WHEN the user changes the language selection mid-session, THE System SHALL translate all existing Simplifications to the new language

### Requirement 7: Session History Management

**User Story:** As a patient, I want to view past medical appointment sessions and their summaries, so that I can review previous visits and track my medical history.

#### Acceptance Criteria

1. THE System SHALL provide a "History" navigation link in the main interface
2. WHEN the user clicks the "History" link, THE System SHALL navigate to the session history page
3. WHEN the history page loads, THE System SHALL fetch all Sessions from the Supabase database via GET /api/sessions
4. WHEN Sessions are retrieved, THE System SHALL display them in reverse chronological order (newest first)
5. WHEN displaying each Session, THE System SHALL show the session title, date, and a preview of the Visit_Summary
6. WHEN the user clicks on a Session, THE System SHALL fetch the full session details via GET /api/sessions/{id}
7. WHEN session details are retrieved, THE System SHALL display the full transcript, all Simplifications, and the complete Visit_Summary
8. THE System SHALL provide a delete button for each Session
9. WHEN the user clicks delete and confirms, THE System SHALL send DELETE /api/sessions/{id} and remove the Session from the database
10. WHEN a Session is deleted, THE System SHALL remove it from the history view immediately

### Requirement 8: Supabase Database Integration

**User Story:** As a system administrator, I want all session data to be stored in a scalable PostgreSQL database, so that the system can handle multiple users and large amounts of data reliably.

#### Acceptance Criteria

1. THE System SHALL use Supabase PostgreSQL as the database backend
2. THE System SHALL create the following tables: sessions, transcript_chunks, simplifications, summaries
3. WHEN a new Session is created, THE System SHALL insert a record into the sessions table with id, title, language, and created_at
4. WHEN a Transcript_Chunk is received, THE System SHALL insert it into the transcript_chunks table with session_id, text, and timestamp
5. WHEN a Simplification is generated, THE System SHALL insert it into the simplifications table with session_id, term, explanation, and timestamp
6. WHEN a Visit_Summary is generated, THE System SHALL insert it into the summaries table with session_id and all structured fields
7. WHEN a Session ends, THE System SHALL update the sessions table with the ended_at timestamp
8. THE System SHALL use connection pooling for database connections to handle concurrent requests efficiently

### Requirement 9: Gemini API Integration

**User Story:** As a developer, I want the system to use Google's Gemini API for all AI-powered features, so that we can leverage advanced language understanding without building custom models.

#### Acceptance Criteria

1. THE System SHALL use the gemini-2.0-flash model for all AI operations
2. THE System SHALL load the Gemini API key from environment variables (GEMINI_API_KEY)
3. WHEN the Backend starts and the API key is missing, THE System SHALL log an error and refuse to start
4. WHEN calling the Gemini_API, THE System SHALL include appropriate prompts for each operation type: simplification, question generation, summary, translation
5. WHEN the Gemini_API returns a response, THE System SHALL parse the JSON response and extract the relevant fields
6. IF the Gemini_API returns an error, THEN THE System SHALL log the error and return a user-friendly error message
7. THE System SHALL implement rate limiting to stay within Gemini API free tier limits (15 requests per minute)
8. WHEN rate limits are exceeded, THE System SHALL queue requests and process them when capacity is available

### Requirement 10: User Interface Design

**User Story:** As a patient, I want a clean and intuitive interface that clearly shows the transcript, simplified terms, and suggested questions, so that I can easily follow the conversation and access information.

#### Acceptance Criteria

1. THE System SHALL display three main panels: Live Transcript, Simplified Terms, and Suggested Questions
2. WHEN the interface loads, THE System SHALL display all panels with clear labels and icons
3. WHEN new transcript text arrives, THE System SHALL append it to the Live Transcript panel with automatic scrolling
4. WHEN new Simplifications arrive, THE System SHALL display them in the Simplified Terms panel with the original term highlighted
5. WHEN new Question_Suggestions arrive, THE System SHALL replace the previous questions in the Suggested Questions panel
6. THE System SHALL provide recording controls: "Start Recording" and "Stop Recording" buttons with clear visual states
7. WHEN recording is active, THE System SHALL display a visual indicator (e.g., red recording icon)
8. THE System SHALL use a responsive layout that works on desktop and tablet devices (minimum width 768px)
9. THE System SHALL use a medical-themed color scheme with high contrast for readability
10. WHEN the translation feature is active, THE System SHALL display translated text in a dedicated panel below the main interface

### Requirement 11: Error Handling and Resilience

**User Story:** As a user, I want the system to handle errors gracefully and continue operating when possible, so that temporary issues don't disrupt my medical appointment.

#### Acceptance Criteria

1. WHEN the Web_Speech_API encounters an error, THE System SHALL log the error and display a user-friendly message
2. WHEN the WebSocket connection fails, THE System SHALL attempt to reconnect automatically
3. WHEN the Gemini_API is unavailable, THE System SHALL queue requests and retry up to 3 times with exponential backoff
4. WHEN the database connection fails, THE System SHALL log the error and return a 503 Service Unavailable response
5. WHEN invalid data is received via WebSocket, THE System SHALL validate the message format and reject invalid messages
6. WHEN a Session cannot be created, THE System SHALL display an error message and prevent recording from starting
7. THE System SHALL log all errors to the console with timestamps and context information for debugging

### Requirement 12: REST API Endpoints

**User Story:** As a developer, I want well-defined REST API endpoints for session management, so that the frontend can retrieve and manage session data reliably.

#### Acceptance Criteria

1. THE System SHALL provide a GET / endpoint that serves the main application HTML page
2. THE System SHALL provide a GET /api/sessions endpoint that returns a list of all Sessions
3. WHEN GET /api/sessions is called, THE System SHALL return JSON with session id, title, language, created_at, and ended_at
4. THE System SHALL provide a GET /api/sessions/{id} endpoint that returns full session details
5. WHEN GET /api/sessions/{id} is called, THE System SHALL return the Session, all Transcript_Chunks, all Simplifications, and the Visit_Summary
6. THE System SHALL provide a DELETE /api/sessions/{id} endpoint that deletes a Session and all related data
7. WHEN DELETE /api/sessions/{id} is called, THE System SHALL delete the Session and all related records from transcript_chunks, simplifications, and summaries tables
8. WHEN a requested Session does not exist, THE System SHALL return a 404 Not Found response
9. THE System SHALL return appropriate HTTP status codes for all responses: 200 OK, 404 Not Found, 500 Internal Server Error

### Requirement 13: Performance and Scalability

**User Story:** As a user, I want the system to respond quickly and handle real-time conversations smoothly, so that the assistance feels natural and doesn't lag behind the conversation.

#### Acceptance Criteria

1. WHEN a Transcript_Chunk is sent to the Backend, THE System SHALL process it and return results within 2 seconds
2. WHEN the Gemini_API is called, THE System SHALL set a timeout of 10 seconds
3. WHEN database queries are executed, THE System SHALL complete within 500ms for simple queries
4. THE System SHALL support at least 10 concurrent WebSocket connections without performance degradation
5. WHEN multiple Transcript_Chunks arrive rapidly, THE System SHALL process them in order without dropping messages
6. THE System SHALL use async/await patterns in Python to handle concurrent operations efficiently
7. WHEN the database grows beyond 1000 Sessions, THE System SHALL maintain query performance through proper indexing

### Requirement 14: Security and Privacy

**User Story:** As a patient, I want my medical conversation data to be handled securely and privately, so that my sensitive health information is protected.

#### Acceptance Criteria

1. THE System SHALL not store audio recordings, only text transcripts
2. THE System SHALL use environment variables for sensitive configuration (API keys, database credentials)
3. WHEN the Gemini_API is called, THE System SHALL use HTTPS for all API requests
4. WHEN the WebSocket connection is established, THE System SHALL use WSS (WebSocket Secure) in production environments
5. THE System SHALL not log sensitive medical information to console or log files
6. THE System SHALL provide a mechanism to delete Sessions and all associated data permanently
7. THE System SHALL not share or transmit patient data to any third parties except the Gemini_API for processing

### Requirement 15: Deployment and Configuration

**User Story:** As a developer, I want clear deployment instructions and configuration options, so that I can set up and run the system in different environments easily.

#### Acceptance Criteria

1. THE System SHALL provide a requirements.txt file listing all Python dependencies
2. THE System SHALL use python-dotenv to load environment variables from a .env file
3. WHEN the Backend starts, THE System SHALL initialize the database schema if it doesn't exist
4. THE System SHALL run on uvicorn with configurable host and port settings
5. THE System SHALL serve static frontend files from the /frontend directory
6. THE System SHALL provide a README.md with setup instructions, API documentation, and usage examples
7. THE System SHALL support deployment to local development environments and cloud platforms (Render, Railway)
8. WHEN deployed to production, THE System SHALL use Supabase PostgreSQL instead of SQLite for data persistence
